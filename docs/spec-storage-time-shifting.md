# 功能規劃：儲能充放（A8 + B5）

- **狀態**：規劃中（待實作）— 對應 Roadmap `A8`（儲能實體模型）、`B5`（儲能充放最佳化），Phase 6
- **日期**：2026-07-29
- **一句話**：把外溢的綠電存下來、在缺口時放出，逐時 CFE 再往上推一段——破題圖第三段「風＋光＋儲」的真實版。

---

## 1. 核心洞見
逐時匹配的鐵律是**嚴格不跨小時**：發電時沒人用就是外溢、用電時沒電就是缺口，兩邊都不能互相抵。示範資料 2024-01 有 **47,947 MWh 外溢**與 **224,374 MWh 缺口**——它們在時間上錯開，所以誰也救不了誰。儲能是唯一能合法打破這條鐵律的東西：**把外溢挪到缺口時段**。

`match_hourly` 的 docstring 本來就寫著「banking would require the storage feature (Roadmap B5)」，這一版就是來兌現那句話的。

## 2. 已定決策
| 項目 | 決定 |
|---|---|
| 儲能歸屬 | **客戶側（表後 BTM）**——電池屬於某個企業客戶，掛在 `customer_id` 下 |
| 充電來源 | **任一案場的外溢綠電（跨合約）**，但**自家合約優先**（見 §5 兩輪規則） |
| 演算法 | **貪婪時序充放**（純函式、確定性、逐步可稽核），不進 MILP |
| 同小時行為 | **有缺口就放電、無缺口才充電**——一具電池不同時充放 |
| 交付範圍 | A8 實體 + 充放層 + 逐時 CFE 視圖；**結算單與 T-REC 不含在內** |
| 定位 | 跨合約充電在轉供實務需另簽約 → UI 標示**情境模擬**（與 B3 多對多同一 register） |

## 3. 設計原則（最小侵入）
**`match_hourly` 一行不改。** 它「嚴格不跨小時」的不變量正是它的誠實之處；儲能是疊在它輸出之上的**獨立一層**，而不是塞進引擎裡的例外：

```
match_hourly → HourlyOutcome（逐時 外溢 / 缺口）
                    ↓
        apply_storage(outcome, batteries, 合約關係)
                    ↓
     調整後的 matched / shortfall / surplus ＋ SOC 序列
```

這與 A7/B4 的手法一致：新能力用新的一層表達，既有的純函式引擎保持可稽核、可回歸。

## 4. 資料層（A8）
新表 `batteries`，欄位刻意最小：

| 欄位 | 說明 |
|---|---|
| `id` / `code`(unique) / `name` | 識別 |
| `customer_id` → `customers` | 客戶側資產（表後） |
| `energy_capacity_mwh` | 容量 |
| `power_mw` | 充放功率上限（充放對稱） |
| `round_trip_efficiency_percent` | 往返效率，預設 **88** |
| `initial_soc_percent` | 期初 SOC，預設 **0** |

- **不放** `status` / 商轉日：「無儲 vs 有儲」的對照由讀數提供，不需要停用旗標（YAGNI）。
- **無 enum 欄位** → migration 不會踩到 Neon 的 `CREATE TYPE` 陷阱。
- CRUD 沿用既有 admin 寫入保護（`ADMIN_WRITE_TOKEN`）。
- **seed**：給用電廠 2（電源管理，日間型、已簽那座光電）一具 **120 MWh / 30 MW / η 88%** 的電池。
  依 2024-01 實測定的規格：該客戶月缺口 5,306 MWh（單日平均 171 MWh、尖峰落在 09:00），
  系統單日外溢平均 1,547 MWh——充電來源綽綽有餘，而 120 MWh × 0.88 ≈ 106 MWh/日的放電量
  約可補掉它六成缺口。選它當示範是因為它**同時簽了風電與那座光電**，兩輪充電規則都會被走到。

## 5. 充放層（B5）—— `app/matching/storage.py`

純函式，簽名概念如下（不依賴 DB、不做 I/O）：

```python
apply_storage(
    outcome: HourlyOutcome,           # match_hourly 的輸出
    batteries: list[Battery],         # capacity / power / efficiency / initial_soc
    contract_farms: dict[int, list[int]],  # customer_id → 有簽約的 farm_id（依合約優先序）
) -> StorageOutcome                   # 充放/SOC 逐時、調整後的 matched/shortfall/surplus、充電來源歸屬
```

每小時 `h` 的規則（可複述、可稽核）：

1. **放電優先**：該客戶在 `h` 有缺口 → `放出 = min(缺口, power×1h, SOC×η)`，SOC 扣 `放出/η`。
2. **無缺口才充電**，分兩輪：
   - **輪 1**：每座案場的外溢先給「**有跟它簽約**」的客戶電池，依既有 contract `priority` / `order`（沿用引擎同一把尺）。
   - **輪 2**：輪 1 之後還有剩的外溢，才開放給其他客戶的電池，依同一優先序。
   - `充入 = min(可用外溢, power×1h, 容量 − SOC)`。
3. **每筆充電記錄來自哪座案場** → 跨合約的度數流向留得住稽核軌跡（未來要做憑證歸屬時的地基）。
4. **SOC 跨日連續**：interval 模式一路走完 744 小時；modeled 模式只有單日 24 點，就是單日循環。
5. SOC 恆夾在 `[0, capacity]`。

**能量守恆的可稽核恆等式**：`Σ放出 = Σ充入 × η`（期末殘留的 SOC 另計）。

## 6. 服務與前端

**Service**（`hourly_matching_service`）新增，沿用 B4 的手法、系統級與逐客戶都有：
`no_storage_cfe_percent`、`storage_uplift_pt`、`soc_by_hour`、`discharged_by_hour`、`charged_by_hour`。

**前端 C6**：
- **三段式讀數**——把 B4 那條擴成完整故事，正好對上破題圖的三個切換：
  `只風電 58.8% → 風光 60.2% → 風光＋儲 X%（+A pt, +B pt）`
- **24h 圖**：儲能放電用**斜線填充帶**——破題圖 `#lg-batt` 已經在用這個視覺語彙（`repeating-linear-gradient`），平台沿用同一套語言；另加 **SOC 曲線**。
- **熱力圖**：早晚缺口時段自然變綠。
- **ⓘ 說明**：新增「儲能時間位移」名詞卡，並在跨合約充電處標示情境模擬。

## 7. 需留意的副作用
- 電池是**新實體**（不像太陽能是沿用 `wind_farms`）→ 需要一支 Alembic migration；但無 enum、無既有資料改動，風險低。
- 逐時服務的兩條路徑（interval / modeled）都要能跑；modeled 只有 24 點，SOC 跨日語意退化為單日循環，需明確標示。
- 跨合約充電讓「這度電算誰的」變得敏感 → 本輪**不動結算與 T-REC**，並在 UI 標示情境模擬；憑證歸屬留到未來。
- 客戶頁／評估頁尚未有電池概念，本輪不動，只在逐時匹配頁呈現。

## 8. 測試（TDD）
- **純函式層**：能量守恆（`Σ放出 = Σ充入 × η`）、SOC 夾在 `[0, 容量]`、功率上限、同一小時不同時充放、SOC 跨日連續、同輸入同輸出（確定性）。
- **回歸保護**：**沒有電池時，outcome 與現況逐位元相同**。
- **兩輪優先序**：自家合約的外溢先被自家電池吃掉，剩餘才輪到別家。
- **service**：`有儲 CFE ≥ 無儲 CFE`、外溢下降、缺口下降。
- **seed 後**：2024-01 有儲 > 無儲。
- 既有 wind／solar 測試不破。

## 9. 交付順序與驗收
1. **A8**：`batteries` 表 + Alembic migration + schema/CRUD + seed 一具電池。
2. **B5 核心**：`storage.py` 純函式 + 單元測試（先紅後綠）。
3. **Service**：整合 + `no_storage_cfe_percent` / `storage_uplift_pt` / SOC 等欄位 + 整合測試。
4. **前端**：三段式讀數 → 放電斜線帶 + SOC 曲線 → ⓘ 說明。
5. **文件**：本 spec 補實作結果、roadmap A8/B5 標記完成、README 補圖與段落。

**驗收**：2024-01 有儲 CFE > 無儲；外溢明顯下降；24h 圖看得出斜線帶把午間／夜間多餘的電挪到早晚缺口；SOC 曲線在容量與功率上限內；全套閘門（ruff／black／mypy／pytest）綠；migration 在 SQLite 與 Postgres 都能升。

**先講清楚的預期量級**：跟 B4 一樣，**系統級數字會被稀釋**——用電廠 1 一家就佔 75% 的用電且沒有電池，所以系統 CFE 大概只動不到 1 pt。真正看得到的是**用電廠 2 自己**：89.4% → 約 95%（一具 120 MWh 電池補掉六成缺口）。這不是缺陷而是結論：**一具企業級電池補得動一家廠的缺口，補不動一個投組的缺口**——要撼動系統數字，得靠配對與簽約結構，不是靠再多裝幾顆電池。UI 的三段式讀數與逐客戶欄位就是為了不讓這件事被平均值蓋掉。

## 10. 未來延伸
- **結算反映充放**：轉供結算單把儲能放出的綠電計進金額，T-REC 跟著走（本輪範圍外）。
- **跨合約的憑證歸屬規則**：把 §5.3 記下的「充電來源」升級成正式的度數溯源。
- **MILP 版充放**：有前瞻能力（知道晚上有大缺口就先存著），可與貪婪版對照看差多少。
- **案場側儲能**：電池掛在案場而非客戶，充放後再走合約分配（引擎同樣零改動）。

---

> 客戶側、跨合約充電、貪婪時序、不動結算——四項決策皆經使用者確認（見 §2）。`match_hourly` 零改動。
